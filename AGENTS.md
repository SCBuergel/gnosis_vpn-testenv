# AGENTS.md — engineering handoff for the regression suite

Read this before changing `scripts/suite/`. Most of it looks obvious until it costs an afternoon of false findings; every item below did. The catalogue of tests is `docs/regression-catalogue.md`; this file is the mechanics and the traps.

## How the suite is shaped

- **There is one run.** `just suite` runs every test, in one order, every time. There are no profiles to pick between: a profile you can choose is a profile someone forgets to choose. Shorten a run with `--very-fast` (aggressive per-test overrides), `--fast` (the catalogue's own shorter durations), `--only`/`--skip` for one test, or a per-test knob `T<NN>_<VAR>=…` (e.g. `T23_DUR=150`), which overrides `--very-fast`.
- **Order inside the run matters.** T03-repeatability-baseline runs third so the run is scored against a band measured on this stack now. T05-loaded-latency runs fifth, right after the throughput reference, because loaded-RTT numbers taken after an hour of other tests measure accumulated host load, not the stack. T06-realtime-udp is placed early for the same reason. Every test lives in exactly one list in `run.sh` or in the runbook — a test in neither is dead code that still looks maintained (T19-background-load and T20-fault-injection were exactly that for a day).
- **Three kinds.** A *gate* can fail the run and must be able to pass on a healthy stack. A *diagnostic* records and never fails the run (a FAIL from one is downgraded to WARN). A *runbook* item is kept but in no run. Every script declares its kind with `suite_kind`. Naming: one hyphenated id everywhere — `T04-fixed-throughput` — in prose and as the verdict/row label in code. The bare number survives only as the file name `t04.sh` and the per-test knob prefix `T04_`.
- **`--very-fast` cannot see anything that needs a long session.** Its arms are 15 s, so a reconnect cycle on the order of a minute (the liveness-ping artifact below took ~85 s) never appears in it. Do not conclude "healthy" from a `--very-fast` run; `--fast` keeps every sustained arm at 90 s or more for exactly this reason.

## Scoring — what a verdict means

- **Absolute assertions are the real signal**: zero reassembly failures, zero `DecapStalled`, every transfer complete, channel membership, shaper present exactly when expected. Throughput and latency are host artifacts on a shared box and are only ever scored **relative to the previous run**, inside the band T03-repeatability-baseline measured.
- **The band has a ceiling.** T03-repeatability-baseline measures its tolerance on the stack under test, so a broken stack measures a huge spread and buys itself a tolerance nothing can fail (±279 % was observed; a delivery collapse from 99.7 % to 17.3 % scored PASS). `BAND_MAX_PCT` (50) clamps it and the verdict says so; T03-repeatability-baseline records `UNSTABLE BASELINE` above the cap. Treat every delta result on such a run as weak evidence.
- **A measurement needs a sample.** A probe with a dead session sends a handful of packets and still prints a confident percentage (255 of 4688 sent, "60.78 % loss"). T06-realtime-udp computes the expected packet count and fails an arm as UNMEASURED below `SAMPLE_MIN_PCT`. Apply the same rule to any new probe.
- **Arms that share a session are not comparable.** Each T06-realtime-udp arm connects for itself; the previous shared session made results order-dependent (82.7 % loss on one arm, 0.41 % on the next).
- **XFAIL is a hard verdict with a tight mechanism**, not a way to silence a test. T13-mtu-sweep keeps one because its shape is reproducible and tied to `hoprnet#8392`; it fails loudly when the shape differs and reports XPASS if the defect vanishes. An XFAIL whose bound came from a number you cannot justify is worse than a plain gate — one was removed from T06-realtime-udp for exactly that.
- **Binary is not the goal; discrimination is.** A gate whose verdict is the same on a broken stack manufactures confidence. T12-balancer-sweep's masking cell is n=1 per tier; check sensitivity before trusting a PASS from it.

## The one trap that cost the most: do not idle before measuring

`connect()` floors its idle at `SURB_RAMP_WAIT` (25 s) so measurements clear the client's SURB ramp. **Do not raise it.** A 75 s default was tried and it manufactured failures: during a long post-connect idle the return-path SURBs expire (`evicting surb … cause=Expired`), the first sustained transfer afterwards starves the return path, the client's tunnel-ping (10 s × 3) times out and the watchdog reconnects — killing whichever transfer ran first. 8/8 first-transfers failed at 75 s on **both** hoprd 4.1.2 and 60269a3; 6/6 passed at a short wait on both. It produced a full day of false "hoprd regression" findings before a control caught it. Ramp length is client-specific (0.96.2: 20 s; older branches: 60 s) and it governs download throughput directly (60 s ramp ≈ 5 Mbit/s, 20 s ≈ 10). If a client needs longer, shorten the ramp (`[connection.surb_balancing.ramp]` / `GNOSISVPN_SURB_RAMP_SECS`); never idle longer. T07-cold-start's cold arm and T15-warmup-knee opt out with `RAMP_WAIT_OPT_OUT=1` because measuring the ramp is their job — that is the only correct reason to set it.

## Running on a host — the operational traps

- **Never `cargo build` on the host while a measurement is running.** Eight vCPUs are shared by the exit, two relays, the client and the target; a build contaminates everything in flight. Chain builds behind runs with a systemd unit that waits.
- **Never edit `lib.sh` (or any test) under a running suite.** Tests source `lib.sh` at start, so a mid-run edit makes the run non-uniform: results before and after are not comparable and you cannot tell which is which afterwards.
- **A run id is a directory and every test appends to it.** `run.sh` now refuses an id that already holds results. Two runs once shared an id and their verdicts blended into one file.
- **Launch long runs as `systemd-run … -p KillMode=process`** so the detached localcluster survives the wrapper exiting — and remember the consequence: `systemctl stop` reports the unit inactive while `just suite`, `run.sh` and the current `tNN.sh` keep running. "Unit inactive" is not "run stopped"; check with `ps` and kill by PID.
- **Never `pkill -f` a pattern that appears in your own command line.** It matches the SSH session that issued it and kills your connection. Anchor patterns (`'^path( |$)'`) or kill by PID.
- **The metrics collector must be able to shed load.** hoprd labels `hopr_surb_balancer_*` by `session_id` and sessions churn constantly, so the series count only grows (52 → 118 in one run, 53 % of all metrics). `configs/otelcol.yaml` carries a `memory_limiter` and a bounded queue because without them the collector reached 14 GB on a 15 GB host and the OOM killer took a running suite with it. The suite's own assertions read hoprd's `/metrics` directly and never depend on the collector.
- **Bring the stack up and let it settle before measuring.** Client channels open on-chain asynchronously; T01-topology-preconditions polls for them rather than sampling once, because a suite launched 15 s after `just up` fails preconditions on a healthy stack.
- **`cluster-restart` rebuilds the chain and races a dying Anvil** ("insufficient token balance at the signer"). Impairment tests apply latency live with `tc netem` on `lo` instead of restarting; `cluster-stop` waits for the chain container to be gone.
- **Channel close is two-phase with a grace period.** A close/reopen inside one run leaves the channel `PendingToClose` and the exit with no usable return relay, which wedges every later test. T09-impairment-ladder is impairment-only for that reason — no channel API calls.

## The harness bug that looked like two product defects: the deadman

`connect()` arms a detached deadman that disconnects the client after `DEADMAN` seconds (900), so the kill switch can never strand a host. Two bugs in that one helper produced a week of wrong findings, and both were found on 2026-09-20.

- **The disarm race.** `disarm_deadman` killed the sleep before the bash, and the bash then fell through `sleep; disconnect`. Every connect made in a subshell (`CLIENT=… bash -c "source lib.sh; connect …"`, as T19 and T22 do) disconnected its own client about 30 s after connect. fullrun5's T22 read zero bytes on five of seven clients with a healthy tunnel ping, and the only trace was one `command=Disconnect` line in 42 000 lines of planner debug. The deadman now uses `sleep && disconnect`, records its own pid, and the disarm kills the bash first. When a rung reads zero bytes on a live tunnel, grep the client log for `command=Disconnect` before anything else.
- **Sessions longer than the deadman.** T23 (3600 s) and T24 (900 s) ran under the 900 s default. The deadman disconnected the client at +15 min, the soak's call counted the remaining 45 min as loss (24 % delivered, exactly 900/3600) and the verdict was PASS because a deadman disconnect is not a reconnect; T24's upload never received its server report and printed a blank loss. That was the suite's "soak death". A test whose session must outlive the default calls `deadman_cover DUR` before `connect`. If a probe shows `IFDOWN` with zero reconnects, suspect the deadman before the stack.

Two smaller rules from the same day. Saved client logs drop the DEBUG path-planner lines (`SAVE_LOG_RAW=1` keeps them): fullrun5 saved 30 GB of them and fullrun6 died at T10 with the disk full. And T22's ladder gate is one-sided, a higher rung may not fall more than `TOL_PCT` below a lower one, because aggregate rising with concurrency is the healthy shape here (10.6, 13.7, 16.1 Mbit/s at 1, 2, 4 clients) and the old "within 25 % of the best rung" rule failed exactly that.

## Versions and builds

- `hoprnet/hoprd` tag `v4.1.2` is on the **5.0 line**; its localcluster writes a config 4.x binaries reject. Use branch `release/4.1` for 4.1.x and tag `v4.0.3` for 4.0.3. Build the localcluster from the same tree as the hoprd binary you run.
- `HOPR_INTERNAL_IN_PACKET_PIPELINE_CONCURRENCY=64` was a workaround for hoprnet #8246 (4.1.0–4.1.2 defaulted decode concurrency to `pool − 2`, ≈1 on small pools). From `release/4.1 @ 60269a3` the default is `available_parallelism × 8` again, so the override is a **no-op** there. Do not read a run with it as a different configuration.
- The #8425 pool arbiter in that build has no config or env surface; it was A/B'd with a patched-in toggle and made **no difference** (6/6 vs 6/6). Do not attribute failures to it without that A/B.
- The client's `release/hoprdv4` branch is the 4.x-compatible line; `main` is the 0.101/5.x line.
- A newer client migrates its keystore in place and the config mount is read-only, so `_client-start` copies the identity into the writable state dir. The client routes RFC1918 around the tunnel, so the traffic target lives on `198.18.0.0/24` with an exit-side MASQUERADE.

## The finding that was wrong for two days: reconnects were the liveness ping, not the load

Every session on this stack reconnected every ~85 s, under any traffic and at idle. That was read as "sustained traffic kills the tunnel" across two full runs, a fast run and a standalone repro, and it was an artifact. The client's periodic tunnel-liveness ping (`tunnel_ping_loop` in gnosis_vpn-lib `core/runner.rs`, 10 s interval, 15 s timeout, 3 misses = reconnect) builds its options from `ping::Options::default()`, whose address is 10.128.0.1, and ignores the `[connection.ping] address` that testenv sets to 10.129.0.1 and that the connect-time verification honours. The server image holds only 10.129.0.1, so every periodic ping timed out. The tells were in the data all along: independence from rate, direction and MTU, and a first ping timeout logged before the load started. A defect caused by load has to depend on the load.

- **Stopgap in testenv:** `server-start` adds `SERVER_PING_ALIAS` (10.128.0.1) to the server's `wggvpn`, so the hardcoded target answers. T01-topology-preconditions fails the run when either the configured or the hardcoded target is missing from `wggvpn`, naming this cause. The real fix is in the client: the periodic loop must use `options.ping_options`.
- **Every reconnect count now carries the tunnel-ping timeout count next to it** (`ping_timeouts` in `log_errors`). Three timeouts per reconnect means the liveness ping is failing; read that before reading load.
- **What is now unattributed and needs a rerun with the alias:** the 1-hour soak going dead at +21 min, parallel flows not scaling (T05 passed once and failed twice), concurrent clients not completing, the intermittent 152 s recovery in T10. None of it can be attributed either way from runs taken with the broken liveness ping.
- **Method rule:** when a failure is independent of every knob you turn, suspect the rig before the product, and look for the earliest error in the log rather than the loudest.
